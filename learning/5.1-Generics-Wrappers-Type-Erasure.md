## 1. Why were Wrapper Classes introduced?

Java has **8 primitive data types**, and each has a matching wrapper class:

| Primitive | Wrapper Class |
|-----------|---------------|
| `byte`    | `Byte`        |
| `short`   | `Short`       |
| `int`     | `Integer`     |
| `long`    | `Long`        |
| `float`   | `Float`       |
| `double`  | `Double`      |
| `char`    | `Character`   |
| `boolean` | `Boolean`     |

A **primitive is not an object.**

```java
int x = 10;
```

Memory:

```
+------+
|  10  |
+------+
```

No object exists — just a raw value.

**Wrapper classes convert primitives into objects.**

```java
Integer x = 10;
```

Memory:

```
Stack                  Heap

x -----------------> +-----------+
                     | value=10  |
                     +-----------+
```

Now `x` is an **object reference**.

### Why do we need Wrapper Classes?

Because many Java features work **only with objects**:

- Collections (`ArrayList`, etc.)
- Generics
- Reflection
- Some frameworks
- Serialization

Example:

```java
ArrayList<Integer> list = new ArrayList<>();   // ✅
ArrayList<int> list = new ArrayList<>();        // ❌ Error
```

## 2. What are Generics?

Generics allow us to write code that works with **multiple types** while maintaining **type safety**.

### Without Generics

```java
ArrayList list = new ArrayList();

list.add("Java");
list.add(10);
list.add(true);
```

Everything is allowed. Retrieving values needs casting:

```java
String s = (String) list.get(0);
```

Wrong casting compiles but blows up at runtime:

```java
String s = (String) list.get(1);   // 💥 Runtime Exception
```

### With Generics

```java
ArrayList<String> list = new ArrayList<>();

list.add("Java");
list.add(10);          // ❌ Compile Error
```

The compiler catches mistakes **early**.

## 3. What does `<T>` mean?

```java
class Box<T> {

}
```

`T` is called a **Type Parameter** — simply a placeholder.

Think of it as:

> *"I'll decide the type later."*

Examples:

```java
Box<String>
Box<Integer>
Box<Student>
```

### Why `T`?

Just convention. You could also write `Box<E>`, `Box<K>`, `Box<V>`.

Common conventions:

| Letter | Meaning |
|--------|---------|
| `T`    | Type    |
| `E`    | Element |
| `K`    | Key     |
| `V`    | Value   |
| `N`    | Number  |

---

## 4. What do `<>` (Angle Brackets) do?

They **specify the generic type.**

```java
List<String>    // this list stores only Strings
List<Integer>   // this list stores only Integers
```

The compiler checks types.

### Diamond Operator

```java
List<String> list = new ArrayList<>();
```

Instead of `new ArrayList<String>()`. The compiler **infers** the type.

---

## 5. What is Type Safety?

### Without Generics

```java
ArrayList list = new ArrayList();
list.add(10);
String s = (String) list.get(0);   // compiles, fails at runtime
```

### With Generics

```java
ArrayList<String> list = new ArrayList<>();
list.add(10);                       // ❌ compiler error immediately
```

## 6. What is Type Erasure?

> One of the most important interview questions.

**Java Generics exist only during compilation.** The JVM does not know what `T` is. The compiler **removes generic information** before creating bytecode.

Example:

```java
class Box<T> {
    T value;
}
```

Compiler roughly converts it into:

```java
class Box {
    Object value;
}
```

This process is called **Type Erasure**.

### Does the compiler create Objects?

**No.** Very important. The compiler only **rewrites code**. Objects are still created at runtime.

```
Compiler:   Rewrite code
Runtime:    Create Objects
```

Example — source code:

```java
Box<Integer> box = new Box<>();
box.set(10);
```

Compiler rewrites:

```java
Box box = new Box();
box.set(Integer.valueOf(10));
```

Still no object yet. Runtime executes `Integer.valueOf(10)` → **now the object gets created.**

---

## 7. Why does Type Erasure happen?

Because the **JVM doesn't understand Generics.**

The JVM only understands real types like `Object`, `String`, `Integer`, `Number`, `Student`.

It does **not** understand placeholders like `T`, `E`, `K`, `V`. So the compiler must remove them.

---

## 8. What is Upper Bound?

Suppose:

```java
class Box<T> {
}
```

The compiler assumes:

```java
class Box<T extends Object> {
}
```

So the **Upper Bound = `Object`** by default.

You can raise the bound:

```java
class Box<T extends Number> {
}
```

Now **Upper Bound = `Number`**.

- Allowed: `Integer`, `Float`, `Double`, `Long`
- Not allowed: `String`

### Why Upper Bound?

```java
class Box<T extends Number> {
    T value;

    void print() {
        System.out.println(value.doubleValue());
    }
}
```

The compiler knows `Number` contains `doubleValue()`, `intValue()`, `longValue()`.

After erasure:

```java
class Box {
    Number value;
}
```

Works perfectly. But if `T` were erased to `Object`:

```java
Object value;
value.doubleValue();   // ❌ Compiler Error — Object has no doubleValue()
```

That's why Java uses the **Upper Bound** as the erasure target.

---

## 9. Why does Java replace `T` with `Object`?

Because **every reference type inherits from `Object`.**

```
Object          Object          Object
   ↑               ↑               ↑
String          Integer         Student
```

One common parent. The compiler can safely erase `T` into `Object`.

---

## 10. Why not replace `T` with `int`?

Suppose `Box<int>`. The compiler tries:

```java
class Box {
    int value;
}
```

Now `Box<String>` would become:

```java
int value = "Hello";   // impossible
```

Similarly `Box<Student>` is impossible. **No primitive can represent every other type.**

---

## 11. Why only Objects in Generics?

The compiler needs **one common type**.

- Objects have `Object` as a common ancestor.
- Primitives (`int`, `double`, `boolean`, `char`) have **no common parent**.

Therefore: **Generics → Objects only.**

---

## 12. Why Wrapper Classes solve it

Wrapper classes convert `int` into `Integer`. Now there's an inheritance chain:

```
Object
    ↑
Number
    ↑
Integer
```

The compiler can erase `Integer` into `Object`. **Problem solved.**

---

## 13. What is Autoboxing?

The compiler automatically converts:

```java
Integer x = 10;
```

into:

```java
Integer x = Integer.valueOf(10);
```

---

## 14. Auto Unboxing

The compiler converts:

```java
Integer x = 10;
int y = x;
```

into:

```java
int y = x.intValue();
```

---

## 15. Does the compiler replace `T` with `Integer`?

**No.** Many beginners think `List<Integer>` becomes:

```java
List {
    Integer value;
}
```

**Wrong.** The compiler actually produces roughly:

```java
List {
    Object value;
}
```

The compiler inserts **casts** automatically where needed.

---

## 16. Does runtime know Generics?

**No.** Runtime only sees `Object`. Generics disappear after compilation.

---

## 17. Why was Type Erasure chosen?

Because Java wanted **backward compatibility.**

- Java 1.4 already had millions of applications.
- Java 5 introduced Generics.

Instead of changing the JVM, the **compiler removes Generics**, so the old JVM continues to work.

---

## 18. Why not specialized generics?

Languages like C# allow `List<int>` to work directly. Java didn't, because:

```
Changing JVM
      ↓
Breaking compatibility
      ↓
Huge ecosystem impact
```

Hence **Type Erasure**.

## 19. Compile-time vs Runtime

| Compile Time | Runtime |
|--------------|---------|
| Syntax checking | Object creation |
| Type checking | Method dispatch |
| Method overloading | Garbage collection |
| Generic checking | Exception handling |
| Type erasure | JIT compilation |
| Autoboxing insertion | |

```

        ↓

        ↓

        ↓

        ↓

```

## Frequently Asked Interview Questions

**Q1. Why do Collections store only Objects?**
Because Collections use Generics, and Generics support only reference types. Primitives don't inherit from `Object`, so wrapper classes are required.

**Q2. Why can't we write `List<int>`?**
Because generics use type erasure, which replaces type parameters with their upper bound (`Object` by default). `int` is a primitive, not an `Object`, so it cannot be used as a type argument.

**Q3. What is Type Erasure?**
The process where the compiler removes generic type information and replaces type parameters with their upper bound (`Object` by default) before generating bytecode.

**Q4. Does Type Erasure happen at compile time or runtime?**
Compile time.

**Q5. Does the compiler create objects?**
No. It only rewrites code. Objects are created later by the JVM at runtime.

**Q6. What is the upper bound?**
The highest type a generic parameter is guaranteed to be. If none is specified, it defaults to `Object`.

**Q7. Why does Java replace `T` with its upper bound?**
Because after removing generics, the compiler still needs a real type the JVM understands. Using the upper bound preserves access to the methods guaranteed by that type.

**Q8. Why not replace `T` with a primitive?**
No primitive can act as a common parent for all types. Only `Object` can represent all reference types.

**Q9. Why are wrapper classes needed?**
They convert primitive values into objects so they can participate in generics, collections, and APIs that require objects.

**Q10. What is the difference between `int` and `Integer`?**

| `int` | `Integer` |
|-------|-----------|
| Primitive | Object |
| Stored directly | Stored as a reference to an object |
| Faster, uses less memory | Slight overhead due to object creation |
| Cannot be used with generics | Can be used with generics |

## Summary

- Primitives are **values**, not objects.
- Wrapper classes make primitive values usable as **objects**.
- Generics provide **compile-time type safety**.
- `T` is a **placeholder**, not a real type.
- During type erasure, `T` is replaced by its **upper bound** (`Object` by default, or a specified bound like `Number`).
- The compiler **never creates objects**; it only rewrites code. The **JVM creates objects at runtime.**
- Generics work only with reference types because only reference types share a common superclass (`Object`). Primitives do not, so wrapper classes are necessary.
